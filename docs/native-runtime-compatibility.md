# Native build and runtime compatibility

## Verified build requests and remaining gap

The two immutable audited Hyprland snapshots request `CMAKE_CXX_STANDARD 26` and search these Lua candidates in order: `lua55`, `lua5.5`, `lua-55`, `lua-5.5`, `lua>=5.5`, `lua<5.6`. Their exact source/version/blob hashes are recorded in [native build profiles](../data/native-build-profiles.json). The source's `CXX_STANDARD_REQUIRED` assignment is metadata; it is not proof that the corresponding effective CMake target property is enforced. A selected compositor's actual compiler, standard library and linked Lua remain unobserved.

CMake’s [`pkg_search_module`](https://cmake.org/cmake/help/latest/module/FindPkgConfig.html#command:pkg_search_module) chooses the first successful alternative. The final two candidates are **not a combined version range**: a generic Lua 5.4 package can pass the last candidate, and a generic Lua 5.6 package can pass the preceding candidate. Named aliases have no version constraint here. `python3 -B scripts/native_selection_probe.py` verifies twelve private synthetic package selections/refusals across both source declarations, including these cases, alias priority and required absence. It never selects a real compositor library or changes packages. Source naming does not establish the selected binary’s ABI.

The application currently links Lua 5.4, with primitive/error-location reference profiles for releases 5.4.6–5.4.9. Its adapter uses C++17. The earlier workspace callback fixtures use C++23/Lua 5.4. These are explicit analysis assumptions, not target compatibility certificates. Source analysis now exposes a collapsed **Native validation incomplete** disclosure identifying its actual model Lua release and the audited source search and C++ request. An unknown profile remains unverified.

`python3 -B scripts/native_build_probe.py --check` independently fetches four bounded immutable source bodies in memory, verifies SHA-256 and Git blob identities, and checks that the API contracts refer to those same commits. No upstream checkout is retained. The two source versions are labels for the audited snapshots, not claims about current latest releases.

## Workspace reference matrix

`scripts/workspace_runtime_probe.py --check` compiles the original argument/object callback bodies under four explicit Lua/C++ contexts: Lua 5.4 and 5.5, each in requested C++23 and C++26 modes. It executes 132 cases per context: the existing 78 argument and 42 object cases, plus twelve numeric-option cases across the two snapshots. Floating arguments retain their exact binary64 bits, including negative zero.

The reference data separates Lua family and observed `std::to_string` behavior. The local GCC 16 profile produces `1.250000`/`-0.000000` in C++23 and `1.25`/`-0` in C++26. This affects numeric layout-option text. The requested language mode alone cannot establish the selected compositor's conversion behavior. The profiler records actual language level, standard-library feature/date, header release, runtime identity, compiler identity and fixture binary hashes separately from portable semantic fixtures.

Regeneration requires all four semantic groups; a check compares every observed group without dropping retained groups that an older standard library cannot produce. All four requested compiler/library contexts must execute. General conversion additionally requires its standard-library feature declaration. Unknown behavior is refused. The approximately 1 MiB reference dataset is a development artifact and is not included in the application binary.

The callbacks retain explicit inert dependencies: primary field parsing/application, selector resolution, real manager state, reload lifetime and native registration policy are not established by this matrix. In particular, these results do not enable `hl.workspace_rule` in ordered replay or establish complete Lua 5.5 language compatibility.

`scripts/workspace_target_profile_probe.py` downloads official [Lua 5.5.0 and 5.5.1 archives](https://www.lua.org/ftp/), verifies reviewed SHA-256 identities, bounds and validates extraction, builds private static libraries, and runs the same matrix separately for each release. Sources, libraries, generated pkg-config entries and binaries are temporary and removed on success or failure. There is no system install. Local execution passes 528 cases for each release, 1,056 executions total. The CI job runs each release independently with an explicit compiler and records the observed identities; its success must be observed on the exact published head.

## Lua 5.5 source and language references

The four existing reference probes now accept an explicit Lua package, compiler, language mode and separate output. Alternate contexts refuse a missing output or the canonical legacy output before fetching or compiling. Twelve refusal checks preserve the existing fixture hashes. Default Lua 5.4 behavior and canonical data remain unchanged.

`scripts/workspace_target_profile_probe.py --source-conformance` additionally checks each private official release through `scripts/lua55_source_probe.py`. Each C++ context compares 100 ordered-language/loader observations, 592 primitive parser observations, 1,064 complex parser observations, 108 path/normalization observations and sixteen dedicated Lua 5.5 cases. Each generated result must match the retained corpus exactly, with only the declared Lua-family description changed for the older corpus. A mismatch refuses; it never generates an accepted override automatically. Reference/tool hashes are checked before and after collection, and the actual profiler records header/runtime identity, language mode and compiler/standard-library metadata.

The dedicated cases exercise global declarations and initialization, declared-name/constant scopes, numeric and generic loop controls, shadowing and nil/false error objects. The [Lua 5.5 manual](https://www.lua.org/manual/5.5/manual.html#8.1) describes language changes, but release and build options both matter: the default official source builds retain compatibility for `global` as an identifier while recognizing declarations contextually. Reserved-global builds are not established by this profile. Loop-control writes fail compilation; a nil error becomes a string. The dedicated reference adapter also uses Lua 5.5's three-argument seeded `lua_newstate`, checks allocator release and limits instructions. The production Lua 5.4 bridge is unchanged; renaming its profile cannot make it a Lua 5.5 bridge.

These are finite trusted fixtures, not complete language support, Tree-sitter grammar coverage, the production compiler adapter, all-setting constraints, native manager effects or selected-compositor conformance. Their data is not embedded in the application, and no saved-model identity or worker admission policy is changed. The [recorded local observation](../data/lua55-source-reference-observation.json) retains both official archive/library identities, profiler metadata, tool/reference hashes and per-corpus result hashes. Both releases pass 1,880 observations in each of C++23 and C++26: 7,520 source/parser/language observations in total, separately from 1,056 workspace executions. Temporary sources and builds are removed. CI repeats these checks with its own observed compiler profile. Production integration still requires all steps below.

The [separate compiler worker](lua55-compiler-worker.md) now implements the bounded compilation/primitive role with shared adapter code and independent Lua 5.5 symbols/seeded construction. Both official releases pass ten process cases, strict lint and optimized image checks; the legacy four-release bridge remains validated. This completes that component, while every integration requirement below remains open unless independently established.

## Known upstream behavior requiring source-model work

The [official issue tracker](https://www.lua.org/bugs.html#5.5.1) was checked on 24 October 2026. Current reports include GC-parameter undefined behavior, NaN loop semantics, signed-zero subtraction optimization and coroutine closing. The compiler component exposes no imported execution, libraries or GC parameters; those boundaries are not a complete dependency-security audit. Older API reader/stack behavior also needs targeted review before production admission.

A [local reproduction](../data/lua-numeric-quirk-observation.json) confirms a **legacy ordered-model discrepancy**: local Lua 5.4.9/5.5.1 produce positive zero for negative zero minus a literal integer zero, while the current Rust source model produces negative zero. Float-zero and variable-zero controls retain negative zero. The [upstream fix](https://github.com/lua/lua/commit/b35736b9d71182bae67492af2a387b3f6e89fd05) changes a compiler optimization. Version strings alone cannot distinguish patched builds. This must be resolved with actual-build compiler observations and source-expression/code-generation coverage before source-model acceptance. Non-integer loops already remain explicit barriers; the finite earlier corpus does not cover every upstream defect. Compilation-only status is separate from evaluated arithmetic values.

## Required production implementation

1. Keep legacy Lua 5.4 reconstruction available for existing saved graphs. Do not rename old profiles, rewrite old model hashes or silently rebuild old saved programs with Lua 5.5. Unknown models remain refused; any explicit profile migration needs fresh review, independent replay, private save/reopen and undo evidence.
2. Build separate, on-demand Lua 5.4 and Lua 5.5 worker images. Unprefixed Lua libraries must not be linked together in one process. Cargo feature unification must not accidentally combine them; build/package each image independently and verify its linked family and compiler identity.
3. Extend compilation, primitive conversion, diagnostics, CST/language handling, ordered evaluation and all API reference probes to exact supported Lua 5.5 releases. A successful compilation is not evidence that the non-executing evaluator understands every accepted construct. Unsupported syntax/effects must retain explicit barriers. Imported Lua must never execute in analysis.
4. Select workers through trusted installed identities and bounded explicit profile choices. Saved paths/integers cannot select executables. Preserve held executable identity, environment/descriptors, no-filesystem/no-network/no-process parser policy, bounded protocol, single-flight/cancellation/deadline behavior, pipe completion and owned child kill/reap on every exit path.
5. Bind every request, response, comparison, private revision, reconstruction and migration to the exact profile. Reject cross-profile replies and stale results. Audit all scalar/monitor/workspace comparisons and unaffected call/load/path/return/effect checks. Model unknown selected-compositor conversion behavior explicitly rather than guessing a numeric option spelling.
6. Exercise both profile images through actual restricted workers and private-display source editing, migration/save/reopen/undo and interruption tests. Then verify packaging, representative memory/latency and native target conformance. Build requests, this reference matrix and a GUI disclosure cannot substitute for those gates.

All original full-product contracts, security gates, preview/apply/recovery and release requirements remain mandatory. This increment makes a compatibility limitation visible and reproducible; it does not certify a complete feature family or release.
