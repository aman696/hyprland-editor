# Immutable source change plans

The source engine can now prepare and review multi-document byte-range changes against an immutable ordered-model input. This is a backend for the graphical source editor; it does not yet expose graphical source edits, persist edited graph revisions, export a changed graph, or write an imported file.

An `EditPlan` pins the entire original program (including all document bytes/load views, snapshot version, loader inputs and supplied path context), current generated model schema and compiler/library profile. Every edit names a logical document, its original content hash, an original UTF-8 byte range, the hash of those exact old bytes, replacement bytes and bounded semantic-target review labels. Labels are data, not feature or filesystem permissions. Preparing sorts edits and expected calls; consuming a plan rejects noncanonical ordering, overlaps, ambiguous adjacent insertions, invalid character boundaries, stale hashes, empty changes and limits violations. The unchanged source remains intact after every success or failure.

Review applies the changes to private copies, preserves every byte outside the requested spans, compiles and reparses every changed document (including unreached dependencies), and reruns the bounded model before and after. It returns only proposed changed document contents with old/new hashes, plan/context fingerprints, compiler/schema identity, explicit model halts and comparison findings. It never turns proposed bytes into a captured-file observation or restores an original read/write capability.

Expected changes specify complete before/after arguments for particular modeled API observations. The original arguments must match exactly. The comparison checks all other modeled API arguments, API/call-site/order identity, loader requests/outcomes, supported branch/loop decision outcomes/sites, root returns and logged module errors. Floats retain their bit distinction, including negative zero. Unexpected argument/call/return findings include their before/after argument snapshots for review. An incomplete original or proposed model cannot receive `modeled_observations_match=true`.

Unchanged recorded loader sites move by the exact preceding byte deltas, with their containing document hashes updated. Their module/cache/path-context identities and supplied target/load-data remain unchanged. Editing a loader request itself is refused pending renewed resolution input. Changing a variable used to compute a module name produces a new unresolved request; it cannot borrow another module's old resolution. Original supplied bindings must have been reached by the original model. These are historical immutable inputs, not current file/absence certificates.

## Safety scope and remaining work

`modeled_observations_match` describes only the supported executed model. Both `ownership_verified` and `runtime_verified` always remain false. An explicit regression appends an uncalled function with an unsupported future effect: the observed calls still match, and neither ownership nor runtime verification is granted. Complete control/future effects, source exclusivity, alias/mount/concurrency identity, generated/config-manager ownership, native acceptance and actual compositor behavior remain separate required work. Two logical load views may refer to one physical file; this backend does not certify that a per-view change can be published independently.

General insertions/deletions can be represented as spans, but callers still need syntax-aware field/trivia ownership, approved printers, intended declaration insertion/removal expectations and impact review. The engine does not assign ownership to comments or manufacture it from a matching result. Module-path editing needs explicit renewed capture/resolution, not guessed rebinding. GUI integration must add generation/session guards, source selection/ownership explanation, shared-value review, edited-graph persistence/undo and reconciliation. These requirements remain in the original audit; this plan engine does not close their contracts.

There are at most 512 edits, 512 expected changed calls and 1 MiB of replacement bytes; each proposed document remains at most 1 MiB. Expected argument trees have depth 64 and a shared 32,768-node cap. Streaming SHA-256 serialization bounds plan/program/review envelopes to 4 MiB without allocating another full JSON string. The existing parser worker additionally enforces its input/output, process-memory, CPU and wall-clock bounds and denies filesystem/network/process creation. Worker-budget failure preserves the input and is not a completed review. Whole-process memory targets remain uncertified.

Nine core tests cover byte/trivia preservation, multi-document rebasing, shared-value impact, branch/call-site changes, computed-loader changes, stale context/schema/compiler/data, overlapping/unsorted/foreign ranges, syntax, new effects, insertion/deletion, partial models, signed zero, size/depth limits and the future-effect counterexample. The real application-worker test checks exact report transport and stale-plan refusal inside isolation. The graphical workflow is a regression check of existing functionality; it does not test a source-edit GUI that has not been connected yet.
