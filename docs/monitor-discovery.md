# Detected outputs and reported modes

Open **Edit Monitors → Output Match → Detected Outputs** and choose **Refresh Outputs**. This reads active and inactive outputs from the Hyprland session selected by the editor's environment. It runs on demand in a background thread; opening the editor does not start polling.

Refresh leaves all draft values unchanged and selects no output automatically. Choose a detected connector to fill the existing output-match controls, then choose **Update Output Match**. Choose a reported resolution/refresh and **Use Mode in Draft** to keep it in that rule. The rule must match that exact connector; fallback, description and other connector rules cannot receive its mode accidentally. The ordinary draft validation, history, undo, save and export paths still apply. Neither action reloads or writes the running compositor configuration.

The picker shows the reported active/inactive state and current resolution/refresh when present. Missing fields remain unknown. Selectable modes use the existing typed dimensions/refresh codec; duplicate strings and unrecognized formats are filtered, with selectable and reported entry counts shown. The picker is not a complete raw hardware inspector. It does not infer display capabilities, decode EDID, verify a mode on the device, resolve effective matching/inheritance or copy the entire live monitor setup.

## Read-only transport and limits

The discovery component uses its existing pinned `ReadSession`: owned runtime/socket checks, process start/boot/executable identity, pidfd and peer credentials, with identity rechecks around requests. Its closed request enum adds only `j/monitors all`, alongside `j/version`. There is no shell, arbitrary command input, setter or external `hyprctl` process. Each request has the existing two-second absolute deadline and 2 MiB response bound.

The monitor JSON parser accepts at most 256 distinct, nonempty connector names. Names and descriptions have 4 KiB limits; control characters in connector names are refused. Optional modes have at most 512 entries per output, each limited to 128 bytes without controls. Invalid types, duplicate known fields, duplicate names and invalid negative/nonfinite numeric values are refused. Unknown JSON fields are ignored; absent optional values are not replaced with defaults. An unknown compositor commit remains an unmapped observation rather than selecting an audited pack by guesswork.

The UI discards results after its window is closed or the draft generation/version changes during discovery. Observations are window-local and are not restored as current hardware state when reopening a saved project. A manual refresh can still become stale after completion; the UI identifies it as an observation, not hardware validation. No persistent service or idle polling is added; the existing background helper checks for completion only while the requested operation is in flight. Existing worker-thread transport bounds apply; this increment does not establish a measured memory or latency budget for the complete application.

## Sources and verification scope

The pinned [Hyprland control implementation](https://github.com/hyprwm/Hyprland/blob/efb50993780079460b0cbed1363e2166a2de1d9f/src/debug/HyprCtl.cpp) provides `getMonitorData` and `monitorsRequest`: `all` includes inactive outputs and JSON contains `name`, `disabled`, dimensions, refresh, position, scale and `availableModes`. The official [monitor documentation](https://wiki.hypr.land/configuring/core/monitors/) describes `hyprctl monitors all`; [mode documentation](https://wiki.hypr.land/configuring/core/monitors/modes/) describes the reported mode strings and possible duplicates.

The discovery tests exercise an actual private Unix socket and assert the two exact read-only request bytes, missing-value behavior, unmapped commits and malformed/oversized payload refusal. The private Xvfb/DBus/XDG graphical fixture supplies controlled observations and exercises refresh, explicit connector selection, mode filtering, match-before-mode validation, draft update/undo, stale/closed-window result disposal, unavailable discovery and narrow-window layout. These fixtures do not connect to the user's desktop or establish physical-display, hotplug, recovery, accessibility or compositor-version conformance. Multi-session selection, event-based refresh, full hardware inspection, isolated rendering and guarded live apply/recovery remain required.
