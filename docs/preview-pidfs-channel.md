# Explicit pidfs channel profile

The numeric-PID channel profile is valid only where selected process IDs are visible to the receiver. A broker inside a private PID namespace can see a parent outside it as PID 0. The new explicit pidfs profile authenticates the kernel's process object instead of treating that translated number as the peer's identity.

`Endpoint::pidfs_pair` and `pidfs_inherited` require supported kernel process-descriptor delivery and a 64-bit pidfs filesystem. `Peer::current_pidfs`, `child_pidfs` and `from_pidfd` retain a live native process capability. An inherited anchor is duplicated and validated; a file path, ordinary file, legacy anonymous-inode pidfd, thread-scoped handle or stored report cannot substitute for it. Endpoint and peer profiles must agree. Unsupported kernels fail without selecting the numeric profile automatically.

Each packet must carry one kernel `SCM_PIDFD` record independently of any `SCM_RIGHTS` frame descriptor. The receiver compares its pidfs device/inode with the retained expected process and checks that the expected process is live before and after reception. Same-user/group credential checks remain in place. On the supported 64-bit pidfs ABI, independent handles for a process share its identity across PID namespace translation. This does not attest executable contents, sandbox boundaries, cgroup membership or projection generation; those remain separate supervisor gates.

The ancillary parser also handles allocation failure. A kernel process-descriptor record can contain a negative error value rather than an installed descriptor. The receiver collects and closes any valid rights, rejects that packet as a fatal identity failure and never constructs an owned descriptor from the negative integer. A private low-descriptor-limit regression fills the table, leaves one slot for a transferred pipe writer, observes identity allocation failure and verifies writer closure and unchanged descriptor count afterwards. That failure is not retried as though no packet was consumed.

Four additional ordinary checks cover a real child using explicit live anchors, rejection of a different live process with matching credentials, profile/ordinary/dead descriptor refusal and thread-handle refusal. Local verification has passed these cases and the exhaustion path. These alone do not prove cross-namespace operation.

The prepared opt-in `pidfs_frame_and_receipt_cross_a_private_pid_namespace` CI fixture places a broker at PID 1 with parent PID 0, outside the GUI's PID namespace. The existing CI provider creates only its future child's namespace, restores that setting and drops privileges before either compiled role. A private bootstrap relays the GUI's sealed synthetic frame and live process anchors. Both roles must exchange exact pixels and a valid receipt, the GUI must clear its buffers, and the private hierarchy must be removed. Positive execution is pending an exact hosted result.

The namespace fixture does not create a user or mount namespace, replace procfs, construct a runtime image, apply syscall/device/network/IPC policy, launch a compositor or route input. Credential mapping across user namespaces, descriptor closure before untrusted execution, signal/descriptor-access restrictions, image attestation and complete lifecycle/crash/resource containment remain mandatory. A process pin carried by a trusted broker must not become untrusted compositor authority. No full preview or security gate is certified.

The implementation follows the kernel's [pidfs identity implementation](https://github.com/torvalds/linux/blob/v6.17/fs/pidfs.c), [filesystem identifier](https://github.com/torvalds/linux/blob/v6.17/include/uapi/linux/magic.h), and [SCM process-descriptor delivery/error handling](https://github.com/torvalds/linux/blob/v6.17/net/core/scm.c). These are ABI references, not a certificate for every kernel or profile.
